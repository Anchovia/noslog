# 마디 수를 뷰어 끝까지 세기 · 초안 경합 정리

- 상태: 유효
- 날짜: 2026-11-02
- 분야: 기능
- 고른 사람: 사용자([재점검 보고](https://claude.ai/artifact/6psh6xDhzzg4jeCmeACFnH) 추천안)

## 맥락

재점검에서 343바이트 초안이 마디 5,000 검사를 지나 공개 뷰어에 표시 819만 개를 만들었다. 모든 한도 안의 문서도 전체 악보로 바꾸면 170초 넘게 멈췄다. 초안 저장 · 열기 · 검토 요청에는 경합이 남아 있었다.

## 결정

- 마디 수는 내용 끝이 아니라 뷰어가 표시를 만드는 끝까지 센다. 내용 끝의 박자로 4마디 뒤까지다. 공개 채보의 표시 수는 바꾸지 않는다.
- `tickToMilliseconds` · `millisecondsToTick` 은 타이밍 배열마다 한 번만 정렬하고 이진 탐색한다. 타이밍 배열을 그 자리에서 고치는 코드는 없다.
- 전체 악보는 패널 밖 트릴 조각을 건너뛴다. 이미 가려지던 조각이라 그림은 같다.
- 저장과 검토 요청은 쓰는 순간에도 상태를 본다. 초안 열기는 잠금 안에서 다시 읽어 같은 채보를 동시에 열어도 하나만 만든다.

## 근거

운영 빌드 · 소프트웨어 WebGL 실측이다. 최악값은 마디 약 4,800 · 타이밍 1,000 · 노트 8,000 · 트릴 200만 틱이다.

| 전체 악보를 처음 누를 때까지 | 전     | 후     |
| ---------------------------- | ------ | ------ |
| 최악값, 폭 1280              | 170초+ | 4.6초  |
| 최악값, 폭 375 · CPU 6배     | 170초+ | 11.9초 |

개발 DB 의 마디 수 최대는 공개 191 · 리비전 261 · 초안 84 로 5,000 을 넘는 문서가 없다. 운영 문서는 재지 않았다.

## 고르지 않은 안

- 쓰기 한도 표의 잠금 대기 시간 초과 고치기: 1,000건 동시에도 한도 수가 정확하고 다른 계정의 실패가 없다
- 초안 열기 · 삭제에 쓰기 한도 추가: 저장량이 늘지 않고 행도 남지 않는다
- 마디 · 트릴 한도 낮추기: 멈춤의 원인이 값이 아니라 계산 방식이었다
