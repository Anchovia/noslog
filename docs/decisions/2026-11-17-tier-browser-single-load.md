# 서열표는 한 번에 받고 검색은 브라우저에서 거른다

- 상태: 유효
- 날짜: 2026-11-17
- 분야: 구조
- 고른 사람: 사용자(추천대로)

## 맥락

관리자 통계에서 `/api/tier-browser` 호출이 다른 API 보다 훨씬 많았다. 서열표는 구간이 화면 가까이 올 때마다 구간별로 요청했고(로그인하면 공개 본문과 내 기록 두 번), 검색어가 바뀌면 개요와 모든 구간을 다시 받았다. 개발 서버에서 로그아웃 기준 끝까지 스크롤 14회, 검색 한 번 16회였다.

## 결정

1. 서열표 전체(곡이 있는 구간 모두)의 공개 본문을 요청 하나(`part=list`)로 받는다. 세션을 읽지 않고 CDN 에 5분 둔다.
2. 내 기록은 로그인했을 때 서열표 전체를 요청 하나(`part=records`)로 받는다. 캐시하지 않는다.
3. 곡 검색은 받아 둔 목록에서 브라우저가 거른다. 보는 칸은 서버 검색과 같다(곡 코드 · 제목 · 가나 · 아티스트 · 승인된 번역 제목, 대소문자 무시 부분 일치). 검색 중의 구간별 곡 수 · 달성 수도 받아 둔 목록에서 센다.
4. 첫 화면(SSR)은 지금처럼 개요와 첫 구간을 함께 그린다. 받아 둔 구간도 화면 가까이 왔을 때 20개씩 그린다.
5. 구간별 요청(`bandId`)은 없앤다. 목록을 받지 못하면 구간마다가 아니라 구간 자리에 오류 한 줄과 「다시 시도」 를 한 번 둔다.
6. 필터 창의 결과 수 미리보기는 고르는 중인 조건이라 받아 둔 목록이 없다. 지금처럼 서버 개요가 검색어까지 센다.

난이도 · 레벨 · 서열표 조건을 바꾸면 개요 · 목록 · 내 기록을 그 조건으로 한 번씩 다시 받는다.

## 고르지 않은 안

- 구간별 로딩은 두고 검색만 요청 하나로 묶기: 실측한 서비스에 같은 방식이 없었다.
- 화면에 함께 들어온 구간을 한 요청으로 묶기: 주소가 조합마다 달라 CDN 캐시 적중이 떨어진다.

## 근거

- [긴 목록 · 검색의 요청 수 — 실제 서비스 36곳](../research/2026-11-17-list-requests.md). 목록 33곳 중 22곳이 처음에 전부 받고, 구간마다 따로 받는 곳은 0곳이다. 검색 19곳 중 9곳이 브라우저에서 거르고 10곳이 검색어마다 1–2회 요청한다. 내 기록을 한 번에 받는지는 미확인이라 2번은 근거 없이 정했다.
- 서열표 전체 응답은 개발 DB(2,159곡 · 구간 15개) 기준 684KB, gzip 154KB 다.
- 2026-10-15 성능 점검 S7(구간 공개 본문과 내 기록 분리 · CDN 5분)의 분리와 캐시는 그대로 두고, 단위만 구간에서 서열표 전체로 바꿨다.
