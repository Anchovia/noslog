## 결정 라벨

- **관찰:** 현재 저장소, 브라우저 또는 승인된 상위 문서에서 검증했습니다.
- **승인:** 사용자가 명시적으로 동의했으며 후속 디자인의 기준으로 사용할 수
  있습니다.
- **제안:** 근거를 바탕으로 제시했으나 사용자의 명시적 승인을 기다립니다.
- **미확정:** 추가 조사, 대표 데이터, 테스트 또는 사용자 결정이 필요합니다.
- **거절:** 검토한 뒤 명시적으로 선택하지 않았습니다.
- **대체:** 이후 승인된 방향으로 교체했습니다.

결정 기록에 중요한 `미확정` 또는 `제안` 항목이 남아 있는 동안 이 기획서
전체를 승인 상태로 취급하지 않습니다.

## 목적

공용 탐색 Surface는 사용자가 서로 다른 두 Catalog를 배울 필요 없이 다음 두
질문 중 하나에 답할 수 있게 해야 합니다.

1. **악곡 범위:** “내가 찾는 악곡은 무엇이며 상세와 기록에 어떻게
   도달하는가?”
2. **채보 범위:** “집중형 뷰어에서 확인하거나 재생할 공개 채보는 무엇인가?”

하나의 검색 위치, Query 모델 및 반응형 상호작용 체계를 재사용하면서도 악곡
항목과 난이도 채보의 의미 차이는 보존해야 합니다.

## 주요 사용 Context

- **승인:** 오락실 플레이 전후의 짧은 검색처럼 불필요한 확인과 숨은 상태가
  큰 비용이 되는 모바일을 주요 Context로 둡니다.
- **승인:** 데스크톱도 필수 대상이며 중앙의 `390px` 휴대폰 Canvas를 유지하지
  않고 추가 너비를 보이는 필터와 결과 비교에 사용해야 합니다.
- **승인:** 이 Surface는 공개입니다. 로그인하면 개인 기록 필터와 기록
  Context를 추가하지만 일반 악곡·공개 채보 탐색에 로그인을 요구하면 안
  됩니다.
- **승인:** 홈은 빈 탐색 요청, 제출한 Query 또는 선택한 홈 미리보기 결과를
  이 Surface로 넘길 수 있습니다.
- **승인:** 홈의 악곡 목적지는 악곡 범위를 엽니다. 홈과 더보기의 채보 뷰어
  목적지는 같은 Surface를 채보 범위가 선택된 상태로 엽니다.

## 현재 제품 근거

### 관찰된 저장소 동작

- `/[locale]/music`이 현재 공개 악곡 탐색 Route입니다.
- 현재 Query는 제목, 아티스트 및 악곡 Index Text 검색을 지원합니다.
- Category, Normal·Hard·Expert·Real 난이도 선택, 난이도별 레벨 범위,
  이름·레벨·최근 플레이·취약점 정렬, 오름차순·내림차순, 목록·Grid 보기 및
  로그인 사용자의 개인 기록 필터 14개를 지원합니다.
- 명시적인 난이도 Query Parameter가 없으면 현재 Normalizer가 Expert와 레벨
  `8–12`만 조용히 활성화합니다.
- Category, 난이도 및 기록 Toggle은 현재 Route를 즉시 교체합니다. 범위 변경은
  `200ms` Debounce 후 반영하고 조작 종료 시 다시 Commit합니다.
- 현재 결과 Query는 Cursor 기반으로 `20`개씩 반환합니다.
- 현재 목록은 `IntersectionObserver` Sentinel이 Viewport에 들어오면 다음
  묶음을 자동으로 가져옵니다.
- 현재 공개 탐색 결과는 악곡 중심입니다. 전용 채보 범위와 공개 난이도
  Grouping은 아직 없습니다.
- 공개 결과 데이터에는 이미 악곡 원문 제목, 선택적인 승인 번역 제목 또는
  일본어 읽기, 아티스트, Category, 배경 및 Normal·Hard·Expert·Real 레벨이
  포함됩니다.
- 비로그인 요청에서는 데이터 계층이 개인 기록 필터와 개인 정렬을
  무시합니다.

### 관찰된 브라우저 기준선

승인된 현재 제품 감사는 좁은 `390px` Viewport와 넓은 데스크톱 Viewport에서
`/ko/music`, `/ja/music`, `/en/music`을 검증했습니다.

- 검색, 필터, 정렬, 보기 컨트롤 및 결과는 문서 단위 가로 Overflow 없이
  사용할 수 있었습니다.
- 현재 넓은 레이아웃은 여전히 일반 `390px` Shell에 시각적으로 제한됩니다.
- 일본어 콘텐츠는 한국어·영어보다 페이지가 길었으며 실제 다국어 라벨과 제목
  길이를 테스트해야 함을 확인했습니다.
- 이 관찰은 현재 기능을 확인한 것입니다. 현재 기본 Expert 필터, 자동 불러오기,
  시각 밀도, 카드 구성 또는 데스크톱 너비를 승인하지 않습니다.

## 승인된 탐색 모델

### 하나의 공용 Surface와 두 범위

- 악곡과 공개 채보 검색에 하나의 공용 탐색 Surface를 사용합니다.
- 검색창 선행 영역에 간결한 범위 선택기를 둡니다.
- 접힌 선택기는 활성 범위 아이콘과 펼침 단서를 사용합니다. 열린 컨트롤에는
  **악곡 검색**과 **채보 검색**의 보이는 다국어 Text를 제공합니다.
- 검색창 위에 악곡·채보 모드 Button 행을 상시 배치하지 않습니다.
- 이후 사용성 근거에서 유지한 Text가 실제 오해를 만든다고 확인되지 않는 한
  범위를 바꿔도 현재 Query를 유지합니다.
- 활성 범위를 공유하고 History에서 복구 가능한 URL 상태로 표현합니다. 정확한
  Path와 Query 문법은 구현 단계 결정으로 남깁니다.
- 검색 단서, 결과 요약, 빈 상태 및 결과 Action이 활성 범위를 보강해야 하며
  아이콘에만 의존하면 안 됩니다.

### 악곡 범위 기본 탐색

- 빈 악곡 범위 Query는 명시적인 묶음 단위로 전체 악곡 Catalog를 노출합니다.
- 초기 Catalog를 Expert 또는 레벨 `8–12`로 조용히 제한하지 않습니다.
- “전체 Catalog”는 모든 이용 가능한 악곡 항목에 도달할 수 있다는 뜻입니다.
  초기 정렬, 카드 밀도 또는 묶음 크기를 아직 결정하지 않습니다.
- 사용자가 선택한 난이도나 레벨 범위는 필터이며 보이지 않는 기본값이 아니라
  적용 상태로 표시해야 합니다.

### 채보 범위 결과 Grouping

- 활성 Query와 필터에 일치하는 공개 채보가 있는 악곡 및 난이도 Target만
  반환합니다.
- 하나의 악곡마다 하나의 결과 카드 또는 결과 단위로 묶습니다.
- 해당 악곡 결과 안에는 일치하는 공개 난이도만 노출합니다.
- 공개 난이도를 선택하면 정확한 집중형 채보 뷰어로 바로 이동합니다.
- 같은 악곡에 속한 난이도마다 시각적으로 독립된 최상위 결과 카드를 만들지
  않습니다.
- 공개하지 않은 난이도를 선택 가능한 것처럼 표시한 뒤 선택 이후 실패를
  설명하지 않습니다.

## 검색 상호작용

### 능동형 Text 검색

- **승인:** 전체 탐색 Surface에서는 IME 입력을 안전하게 처리하며 추가 Text
  입력이 없는 `300ms` 후 결과를 갱신합니다.
- 일반 Text 결과 좁히기에 별도 검색 Button 클릭을 요구하지 않습니다.
- 결과가 없어도 사용자의 Query를 유지합니다. 오류 복구를 위해 검색창을
  지우지 않습니다.
- Enter는 현재 Query를 즉시 Commit할 수 있지만 의미가 다른 두 번째 검색
  동작을 만들면 안 됩니다.
- 새로운 Query나 범위 변경은 이전 결과를 무효화합니다. 순서가 뒤바뀐 응답이
  현재 상태의 결과를 교체하면 안 됩니다.
- 안정된 Query를 Commit한 뒤 URL을 갱신할 수 있지만 글자 입력마다 History
  항목을 만들어 뒤로가기를 사용할 수 없게 하면 안 됩니다.

### 홈 인계

- Target이 모호하지 않으면 홈 미리보기 선택이 관련 악곡 상세 또는 집중형 채보
  Target을 바로 열 수 있습니다.
- 홈의 `전체 결과 보기` Action은 정확한 Query와 범위를 유지해 이 Surface를
  엽니다.
- 홈에서 빈 값을 제출하면 빈 `q` Parameter 없이 선택한 범위의 탐색 상태를
  엽니다.
- 전체 필터, 정렬, 묶음 불러오기 및 결과 복구는 이 Surface가 담당하며 홈에서
  복제하지 않습니다.

## 필터 적용 모델

승인된 모델은 모든 상황에 하나의 `즉시 반영` 또는 `적용` 규칙을 사용하는
것이 아니라 반응형이며 과업 특성에 따라 달라집니다.

### 모바일 및 결과가 가려지는 레이아웃

- 결과 Collection을 컨트롤 옆에서 의미 있게 유지할 수 없다면 필터를 전체
  화면 또는 화면 대부분을 차지하는 Layer로 엽니다.
- 가려진 결과 Collection을 선택마다 교체하지 않고 여러 Category, 난이도,
  범위 및 개인 기록 변경을 임시로 선택할 수 있게 합니다.
- 행정적인 확인이 아니라 결과 과업으로 복귀하는 하나의 고정 주요 Action을
  사용합니다. 라벨은 **결과 보기**, 유효한 결과 수가 준비되면
  **N개 결과 보기**를 사용합니다.
- 주요 Action은 임시 조건을 Commit하는 동시에 필터 Layer를 닫습니다. 적용
  뒤에 두 번째 닫기 Action을 요구하지 않습니다.
- 결과 수 계산 중에도 일반 **결과 보기** 라벨을 사용할 수 있어야 하며 결과
  수 계산이 완료를 막으면 안 됩니다.
- 뒤로가기 또는 닫기는 임시 변경을 Commit하지 않고 종료하며 이전에 적용한
  필터 상태를 복구합니다.
- Layer를 닫은 뒤 적용 필터를 결과 요약 근처에서 계속 확인할 수 있어야
  합니다.

이는 과업 단계를 추가한 것으로 취급하지 않습니다. 결과가 가려지는 Layer의
사용자는 어느 모델에서든 결과로 돌아가야 하며 주요 Action이 필요한 복귀와
필터 Commit을 하나로 합치기 때문입니다.

### 데스크톱 및 결과가 보이는 레이아웃

- 노출된 필터 컨트롤 옆이나 가까이에 주요 결과 Collection을 계속 보이게
  합니다.
- 사용자가 결과 변화를 볼 수 있으므로 개별 필터 선택을 즉시 반영합니다.
- Text와 유사하거나 연속적인 컨트롤은 Debounce합니다. 범위 컨트롤이 Pointer
  1 Pixel마다 결과 요청을 보내면 안 되며 짧은 안정 구간 이후 또는 조작
  Commit 시 갱신합니다.
- 필터 컨트롤은 안정적으로 유지하고 결과 영역만 Loading을 전달합니다.
- 전체 페이지를 Remount하지 않고 Focus와 가까운 Scroll Context를 보존합니다.

### 적용 상태 Action

- 결과 요약에서 적용 필터 하나를 제거하면 모든 Viewport에서 즉시 반영합니다.
- 모든 적용 필터 초기화도 즉시 반영하며 활성 범위의 승인된 기본 탐색 상태로
  복구합니다.
- 적용 조건, 결과 수 및 결과는 같은 Commit 상태를 설명해야 합니다. 모바일의
  임시 선택을 이미 적용된 것처럼 표시하면 안 됩니다.
- 결과 집합을 바꾸는 필터와 정렬은 묶음 불러오기를 첫 묶음으로 초기화합니다.
- 모든 Viewport에 확인 단계를 추가하는 대신 요청 취소, 오래된 응답 거부 및
  Cache·Query 최적화로 성능을 보호합니다.

## 명시적인 점진적 불러오기

- Scroll 위치를 기준으로 결과를 자동으로 더 불러오지 않습니다.
- 다음 묶음이 있으면 현재 Collection 뒤에 명확한 **더 보기** 컨트롤을
  제공합니다.
- 신뢰할 수 있는 데이터가 있으면 전체 일치 결과 수와 현재 표시 범위를
  보여줍니다.
- 컨트롤은 다음 동작을 예측할 수 있게 해야 합니다. 묶음 크기 결정 승인 후
  다음 묶음 수를 라벨에 포함할 수 있습니다.
- 활성화하면 이미 보이는 Collection을 제거하거나 재정렬하지 않고 다음 묶음을
  추가합니다.
- Loading 중에도 컨트롤 위치를 안정적으로 유지하고 적절한 Busy 상태를
  노출합니다.
- 증분 불러오기 실패 시 기존 결과를 유지하고 같은 위치에서 재시도를
  제공합니다.
- 더 이상 결과가 없으면 Action을 제거하거나 명확한 끝 상태로 대체합니다.
  설명 없이 비활성화된 컨트롤을 남기지 않습니다.
- 악곡 상세나 집중형 채보 뷰어에서 복귀할 때 범위, Query, 적용 필터, 정렬,
  불러온 Cursor·묶음 상태 및 의미 있는 Scroll 위치를 복구할 수 있어야
  합니다.

정확한 묶음 크기는 의도적으로 미확정이며 대표 카드 밀도, 서버 응답 시간,
모바일 Memory 및 복귀 상태 동작과 함께 테스트해야 합니다.

## 콘텐츠 및 기능 요구사항

### 항상 제공하는 구조

1. 일반 반응형 헤더와 건너뛰기 Link
2. 페이지 정체성과 간결한 활성 범위 Context
3. 범위를 인식하는 검색창
4. 필터 및 정렬 진입
5. Commit된 필터 상태가 있는 결과 요약
6. 악곡 또는 채보 범위 결과 Collection
7. 필요할 때 명시적인 점진적 불러오기 컨트롤
8. 일반 푸터

최종 시각 순서와 Grouping은 너비에 따라 적응할 수 있지만 검색, Commit된
상태, 결과 및 복구 컨트롤은 명확한 의미 관계를 유지해야 합니다.

### 필수 결과 데이터

#### 악곡 범위

- 안정적인 악곡 식별자
- 원문 제목
- 활성화되어 있고 사용할 수 있을 때 선택한 승인 한국어·영어 제목 또는
  일본어 읽기
- 사용할 수 있을 때 아티스트
- Category Context
- 이용 가능한 난이도와 레벨 정보
- 선택하면 악곡 상세가 열린다고 예측할 수 있는 충분한 목적지 Context
- 로그인했으며 승인된 필터 또는 정렬 동작과 관련 있을 때만 개인 기록 Context

#### 채보 범위

- 안정적인 악곡 식별자와 정체성
- 원문 및 선택한 번역·읽기 제목 처리
- 악곡을 구분하는 데 유용할 때 아티스트
- 일치하는 공개 난이도 Target만 표시
- 선택 가능한 모든 Target의 난이도와 레벨
- 선택 가능한 난이도마다 직접 연결되는 명확한 집중형 뷰어 목적지

정확한 시각 Field, 재킷 비중, 기록 요약 밀도 및 목록·Grid 보기 제공 여부는
미확정입니다.

## 반응형 요구사항

### 좁은 레이아웃

- 범위 인식 검색, 간결한 Commit 상태, 결과, 명시적인 더 보기 순서로 하나의
  강한 세로 과업 흐름을 유지합니다.
- 밀도 높은 필터를 영구 콘텐츠 열에 두지 않고 승인된 결과 가림 필터 Layer로
  엽니다.
- 모바일 전용 하단 내비게이션이나 범위·필터 Button 행을 상시 추가하지
  않습니다.
- Software Keyboard, 한국어·일본어 IME 조합, 브라우저 Chrome 및 낮은
  Viewport 높이가 필터 완료 Action을 가리지 않아야 합니다.
- 결과 카드는 긴 일본어 제목과 여러 줄 번역 Caption을 가로 Overflow 없이
  처리해야 합니다.

### 넓은 레이아웃

- `390px` 모바일 Canvas를 데스크톱 전체로 늘리지 않습니다.
- 추가 너비를 사용해 노출된 필터 Rail 또는 영역과 결과를 함께 보이게 하고
  악곡·난이도 비교를 개선합니다.
- 데스크톱 전용 분류 체계를 만들지 않고 하나의 검색·범위 모델을 보존합니다.
- 검색, 필터 또는 결과 비교를 지원할 공간에 무관한 공지나 내비게이션을
  배치하지 않습니다.
- 대표 결과 카드 테스트 이후 읽기 좋은 외부 콘텐츠 경계를 정합니다. 정확한
  Container와 열 Token은 미확정입니다.

## 접근성 요구사항

- 활성 범위를 포함하거나 Programmatically 연결한 명시적인 검색창 접근 가능
  이름을 제공합니다.
- 간결한 범위 선택기는 선택 값, 펼침 상태, 제어 Popup, Keyboard 동작, 보이는
  Text 선택지 및 예측 가능한 Focus 복귀를 노출해야 합니다.
- 검색 갱신마다 Focus를 이동하면 안 됩니다.
- 결과 수 갱신은 절제된 Live Region 의미를 사용하며 중간의 오래된 응답을
  읽으면 안 됩니다.
- 모바일 필터 Layer에는 접근 가능한 이름, Modal 상태의 Focus 제한,
  Escape·뒤로가기 동작 및 Trigger로의 Focus 복귀가 필요합니다.
- 모바일 완료 Action은 브라우저 Zoom과 낮은 Viewport 높이에서도 도달할 수
  있어야 합니다.
- 필터 적용은 이해 가능한 결과 갱신을 제공해야 합니다. 모바일 Commit 후
  정확한 Focus 목적지는 접근성 Prototype의 미확정 결정이며 사용자의 읽기
  Context를 갑자기 버리면 안 됩니다.
- 적용 필터 제거 컨트롤의 접근 가능한 이름에는 Category와 값을 포함합니다.
- **더 보기**는 Keyboard로 작동하는 명시적 컨트롤이어야 합니다. 추가 이후
  Focus를 예측할 수 있고 강제 Focus Jump 없이 새 범위를 이해할 수 있어야
  합니다.
- 의미 있는 결과 Heading·목록과 하나의 페이지 단위 `main` Landmark를
  사용합니다.
- 범위, 필터, 초기화, 결과 및 점진적 불러오기 컨트롤은 WCAG 2.2 Target 크기
  또는 Target 간격 요구사항을 충족합니다.

## 다국어 요구사항

- 모든 보이는 라벨과 접근 가능한 라벨을 한국어, 일본어 및 영어에서
  검증합니다.
- 악곡 원문 제목을 주요 정체성으로 보존합니다.
- 제목 표시 설정을 켰으면 승인된 한국어·영어 제목 또는 일본어 읽기를 원문을
  대체하지 않는 보조 Text로 표시합니다.
- 유일한 식별 제목을 잘라내지 않습니다. 모호한 말줄임보다 여러 줄 처리를
  우선합니다.
- Text 검색과 `300ms` 유휴 Trigger는 한국어·일본어 IME 조합을 안전하게
  처리해야 합니다.
- 동적 결과 수, 표시 범위 및 더 보기 수량은 Locale에 맞는 숫자와 문법 처리가
  필요하며 안전하지 않은 문자열 연결로 만들면 안 됩니다.
- 페이지 패밀리 승인 전에 세 언어의 범위, 필터, 난이도, 결과 상태, 재시도 및
  끝 상태 Copy를 모두 준비해야 합니다.
- 번역하면 공유나 구현 Mapping이 깨지는 Query·필터 URL 값에는 안정적인 기술
  식별자를 유지합니다.

### 근거의 수렴

- 결과가 계속 보이고 동작이 단순하며 응답 성능이 안정적이면 능동 갱신이 가장
  유용합니다.
- 사용자가 여러 관련 조건을 고르거나 결과가 가려지면 묶음 Commit이 가장
  유용합니다.
- 모바일 적용은 필요한 결과 복귀를 함께 수행할 때만 저마찰 방식입니다. 적용
  뒤에 별도 닫기를 요구하면 피할 수 있는 작업을 추가합니다.
- 갱신 방식과 관계없이 Query, Commit 필터, 결과 수 및 보이는 결과가 서로
  모순되면 안 됩니다.
- 모든 Viewport에 확인 단계를 추가하기 전에 안정된 입력, 요청 취소, Cache 및
  국소적인 결과 Loading으로 성능을 보호해야 합니다.

### 근거의 차이와 NosLog의 해결

- Visa와 DWP는 묶음 필터를 선호하고 SAP는 가능하면 능동 갱신을 선호합니다.
  Carbon, Dell, NSW, Siemens, Maersk 및 Baymard는 필터 복잡도, 결과 가시성,
  응답 시간 또는 Viewport에 따라 선택합니다.
- NosLog는 한 출처를 보편 규칙으로 택하지 않고 승인된 반응형 혼합형으로 이
  차이를 해결합니다.
- Algolia와 Elastic은 기술적 가능성을 보여주지만 상호작용 자체의 근거가
  되지는 않습니다. 후속 구현은 측정한 지연, 요청 취소 및 접근성 요구사항을
  충족해야 합니다.

## 거절되거나 대체된 대안

- **별도 중복 채보 검색 페이지 — 대체:** 명시적인 악곡·채보 범위를 가진 하나의
  탐색 Surface를 유지합니다.
- **악곡·채보 상시 Button 행 — 거절:** 간결한 선행 선택기를 사용하고 Text
  단서와 결과로 범위를 보강합니다.
- **숨은 Expert `8–12` 초기 필터 — 거절:** 초기 악곡 탐색은 이용 가능한 전체
  Catalog를 포함합니다.
- **채보 난이도마다 최상위 카드 하나 — 거절:** 같은 악곡의 일치하는 공개
  난이도를 악곡 정체성 아래에 묶습니다.
- **결과 없음에서 Query 지우기 — 거절:** 사용자의 입력을 유지하고 수정할 수
  있게 합니다.
- **모든 상황의 즉시 필터 — 거절:** 결과를 가리는 모바일 Layer가 선택마다
  보이지 않는 콘텐츠를 바꾸고 반복 요청을 만듭니다.
- **모든 상황의 적용 필터 — 거절:** 결과가 보이는 데스크톱에서 유용한 Feedback
  없이 확인 단계를 추가합니다.
- **모바일에서 적용 후 닫기 두 Action — 거절:** 하나의 **결과 보기** Action이
  Commit과 복귀를 함께 수행합니다.
- **자동 무한 Scroll — 거절:** 복구 가능한 증분 상태와 Context 복구를 갖춘
  명시적인 더 보기를 사용합니다.
- **내부 Scroll이 있는 홈 5개 결과 미리보기 — 상위 문서에서 거절:** 홈 안에
  두 번째 Scroll 영역을 넣지 않고 이 페이지에 전체 탐색을 넘깁니다.

1. Query가 비어 있을 때 악곡 범위와 채보 범위의 초기 정렬은 무엇인가?
2. 두 범위가 함께 쓰는 필터·정렬과 악곡 또는 채보 전용 항목은 무엇인가?

   기록 필터를 어떻게 제공할 것인가?
4. 모바일·데스크톱 밀도에서 악곡·채보 결과 카드에 어떤 정보를 넣고 목록·Grid
   전환을 사용자가 계속 제어하게 할 것인가?
5. 어떤 묶음 크기와 더 보기 Copy가 탐색, 응답 시간, Memory 및 복귀 상태
   복구의 최선 균형을 만드는가?
6. Text 불일치, 과도한 필터 조건 및 공개 채보 없음에 따라 어떤 결과 없음 복구
   Action을 먼저 둘 것인가?
7. 모바일 필터 Commit 후 Focus를 복귀한 필터 Trigger에 유지할지, 결과 요약으로
   옮길지, 입력 방식에 따른 조건부 규칙을 사용할 것인가?

## 브라우저 검증 대상

후속 구현은 최소한 다음을 검증해야 합니다.

- 악곡·채보 범위의 `/ko/music`, `/ja/music`, `/en/music`
- 홈·더보기 직접 진입, 빈 탐색, Query 인계, URL 공유, 새로고침, 뒤로가기 및
  앞으로가기 복구
- `300ms` 안정 검색을 사용하는 한국어·일본어 IME 조합
- 활성 요청 중 Query, 범위 및 필터 변경과 의도적으로 순서를 바꾼 응답
- 숨은 난이도 제한 없는 전체 악곡 초기 탐색
- 일치하는 공개 난이도 0개, 1개 및 여러 개인 채보 Grouping
- 공개 난이도에서 집중형 뷰어로 직접 진입하고 정확한 복귀 상태 복구
- 모바일 필터 임시 선택, 일반·결과 수 포함 Action, 취소, Commit, 하나 제거 및
  전체 초기화
- 데스크톱 개별 필터 즉시 반영과 범위 컨트롤 Debounce·Commit
- 비로그인·로그인 개인 필터 상태
- 초기 Loading, 느린 응답, 결과 없음, 조회 오류, 증분 Loading, 증분 오류,
  재시도 및 결과 끝
- Viewport에 의한 요청 없이 명시적인 더 보기
- 가로 Overflow가 없는 좁은 `390px`, 낮은 높이 모바일, 브라우저 Zoom 및 대표
  데스크톱 너비
- 긴 일본어 원문 제목, 한국어·영어 번역 Caption, 아티스트 없음, 번역 없음 및
  Real 없음 데이터
- Keyboard만 사용하는 범위, 검색, 필터, 결과 선택, 더 보기, 재시도 및 복귀
- Focus 순서, Focus 복귀, 상태 알림, Landmark, Target 크기, 모션 감소 및
  브라우저 Console 오류

## 이 기획서의 승인 기준

- 하나의 공용 Surface 안에서 악곡·채보 범위의 의미 차이를 유지합니다.
- 초기 악곡 탐색에 숨은 Expert `8–12` 제한이 없습니다.
- 공개 채보 결과를 악곡별로 묶고 사용할 수 없는 Target을 노출하지 않습니다.
- Text 검색, 모바일 필터 Commit, 데스크톱 능동 필터 및 적용 상태 제거에
  충돌하지 않는 명시적인 규칙이 있습니다.
- 자동 무한 Scroll이 없으며 명시적인 점진적 불러오기에 Loading, 재시도, 끝 및
  복귀 상태 요구사항이 있습니다.
- 현재 구현 사실을 승인된 2.0 동작으로 잘못 표시하지 않습니다.
- 모바일과 데스크톱이 하나의 제품 모델을 공유하면서 결과 가시성과 공간에
  맞게 적응합니다.
- 한국어·일본어·영어, 접근성, 성능 및 브라우저 검증 요구사항을 기록합니다.
- 해결하지 않은 중요한 선택은 모두 `미확정` 또는 `제안`으로 명확히 남깁니다.
- 문서를 `승인` 상태로 바꾸기 전에 사용자가 남은 결정 기록을 명시적으로
  승인합니다.
