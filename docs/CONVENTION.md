# NosLog 협업 컨벤션

커밋·브랜치·Issue·PR 작성 기준을 관리한다. 코드 작성과 의존 방향은
[코드 스타일](./code-style.md), 디자인 값과 동작은 [디자인 가이드](./design/README.md),
에이전트 작업 권한과 운영 DB·릴리스 절차는 [AGENTS.md](../AGENTS.md)를 따른다.

## 커밋

```text
<type>: <대상> <동작 명사>

<무엇이 왜 바뀌었는지 문장으로, 필요한 경우>

Closes #123 (관련 이슈를 완료한 경우)
```

| 타입       | 용도                                 |
| ---------- | ------------------------------------ |
| `feat`     | 사용자 기능 추가                     |
| `fix`      | 오류 수정                            |
| `refactor` | 동작을 유지하는 구조 개선            |
| `style`    | 포맷·import 정렬 등 동작 없는 변경   |
| `docs`     | 문서 변경                            |
| `test`     | 테스트 추가·수정                     |
| `chore`    | 개발 도구·설정·의존성·CI 변경        |
| `release`  | 버전 갱신 (`release: NosLog vX.Y.Z`) |

### 제목

- 제목 하나에 변경 하나만 적는다. 변경이 둘 이상이면 커밋을 나눈다. 같은 파일에 섞여 나눌 수 없으면 제목에는
  두 변경의 공통 목적을 쓰고, 각 변경은 본문에 적는다.
- 설명은 「대상 + 동작 명사」로 쓴다. 조사는 줄이고, 낱말이 이어져 뜻이 흐려질 때만 넣는다.
- 끝 낱말은 아래 열두 개 가운데 고른다. `release` 만 표의 형식을 그대로 쓴다.

    ```text
    추가  수정  변경  구현  제거  적용
    해결  삭제  반영  설정  분리  개선
    ```

- 가운뎃점, 줄표, 화살표, 「및」, 괄호 설명을 쓰지 않는다. 쉼표로 변경을 늘어놓지 않는다.
- 50칸 안으로 쓰고 72칸을 넘기지 않는다. 한글은 두 칸, 영문과 숫자, 기호, 공백은 한 칸으로 세고 `type: `도
  포함한다. `fix: ` 뒤가 한글만이면 22자가 50칸, 33자가 72칸이다.
- 끝에 마침표를 붙이지 않는다.
- 그 작업의 대화나 보고에서만 통하는 번호나 이름(「점검 1–7번」)을 쓰지 않는다. 기록만 보고 무엇이 바뀌었는지
  알 수 있게 쓴다.

```text
fix: 뮤즈캣 오락실 캐시 사용자별 분리
fix: 업로드 이미지 실제 형식 검사 추가
fix: 기체 가동 확인 중복 저장 문제 해결
```

아래처럼 쓰지 않는다.

```text
fix: 알려진 웹 취약점 점검 1–7번 수정
fix: 로그아웃 때 세션 폐기 · Discord 계정 변경 재확인 · 업로드 파일 머리 검사
fix: 기체 가동 확인 중복 저장 막기
```

### 본문

- 제목만으로 무엇이 왜 바뀌었는지 알 수 없을 때 쓴다. 사용자가 겪는 동작이 달라지는 변경, 한 커밋에 변경이
  둘 이상 묶인 경우, 배포 전에 할 일이 있는 경우가 그렇다. 문서나 오타, 이름 바꾸기처럼 제목이 전부인 커밋에는
  쓰지 않는다.
- 제목 다음에 빈 줄을 두고 쓴다. 한 줄은 72칸을 넘기지 않는다.
- 문장으로 쓴다. 글머리표 목록, 굵은 글씨, 머리말, 가운뎃점, 줄표, 화살표를 쓰지 않는다.
- 왜 바꿨는지를 적는다. 바뀐 코드를 다시 설명하지 않는다. 결정 기록이 있으면 내용을 되풀이하지 않는다.
- 세 줄을 넘으면 커밋을 나눌 수 있는지 먼저 본다.
- 관련 이슈 번호는 선택 사항이다. 본문 끝에 완료면 `Closes #123`, 참조면 `Refs #123`을 쓴다.
- 서명·도구 홍보 문구를 커밋·PR·릴리스 본문에 추가하지 않는다.

```text
fix: 로그아웃 시 전체 기기 세션 폐기 적용

쿠키만 지우던 로그아웃이 세션 버전을 올려 다른 기기도 함께 끊는다.
탈퇴로 사용자가 없어진 쿠키도 로그아웃으로 돌려준다.
```

### 에이전트

- 에이전트는 커밋마다 제목과 필요한 본문을 정하고 커밋 스크립트로 준다. 스크립트를 실행하는 것을 비롯한 Git 변경
  작업은 사용자가 한다. 스크립트 만드는 법은 [AGENTS.md](../AGENTS.md)의 「사용자 규칙」에 있다.

기준의 근거는 [커밋 제목 조사](./research/2026-11-11-commit-titles.md)와 결정 두 개
([길이와 본문](./decisions/2026-11-11-commit-message.md), [양식](./decisions/2026-11-11-commit-format.md))에 있다.

## 브랜치와 병합

- 기존 `dev` 개발·`main` 릴리스 흐름을 유지한다.
- 작업 브랜치가 필요하면 `codex/<영문 소문자와 하이픈>`을 기본으로 하되 사용자의 지정 이름을 우선한다.
- 별도 작업 브랜치의 PR은 `dev`, 릴리스 PR은 `dev`에서 `main`으로 보낸다.
- 브랜치 생성·동기화·병합·삭제는 사용자가 한다. 이 문서는 새 병합 방식을 강제하지 않는다.
- GitHub 릴리스는 릴리스 PR이 합쳐진 뒤, `main`의 버전과 태그를 확인하고 게시한다.
  상세한 불변 태그 규칙은 AGENTS.md의 「릴리스」 절을 따른다.

## Issue

기존 기능 제안·버그 제보·데이터 수정 폼을 유지한다. UI·접근성, 리팩터링,
테스트, 개발 환경, 문서 작업에는 해당 전용 폼을 사용한다.

- 문제와 필요한 이유, 작업 범위, 완료 조건을 적는다.
- 검증에 필요한 언어·화면 폭·권한·데이터 상태를 관련된 경우 함께 적는다.
- 리팩터링은 Before/After와 보존 조건, 테스트는 재현 시나리오·mock/격리 환경, 문서는 원본·코드/명령/링크 확인을 적는다. UI·환경 양식에는 실측·호환성 예시가 있다.
- 캐시 변경은 [코드 스타일의 캐시 검증](./code-style.md#cache-changes)에 따라 키/태그/경로와 저장 후 영향을 받는 화면을 적는다.
- 비밀값·계정 토큰·DB 주소·개인정보를 첨부하지 않는다.
- 비공개 보안 문제는 공개 Issue에 재현 상세나 비밀값을 올리지 않고 운영자에게 전달한다.
- Issue 작성이 작은 수정의 필수 선행 조건은 아니다.

## Pull Request

[기존 PR 템플릿](../.github/pull_request_template.md)을 사용한다.

- 제목은 커밋과 같은 `type: 한국어 설명` 형식이다. 릴리스 PR은 직전 릴리스 양식을 따른다.
- 문제와 변경 결과를 먼저 설명하고 영향받는 기능·화면을 적는다.
- 버전·DB 마이그레이션·환경 변수·의존성·외부 API 영향 여부를 명시한다.
- 실행한 검사는 결과와 함께 적는다. 실행하지 못한 검사는 이유를 적고 체크하지 않는다.
- 공용 UI 변경에는 Storybook 스토리·동작·접근성 검사와 영향을 받는 화면 검증을 포함한다.
- 토큰과 부품 규칙의 변경은 가이드·결정 기록·테스트를 함께 맞춘다.
- 저장·제출·삭제를 포함하는 E2E는 AGENTS.md의 격리 환경 절차를 따른다.

## 파일·경로 정리

- 코드·스타일 파일과 내부 폴더는 kebab-case, React 컴포넌트 이름은 PascalCase를 쓴다.
- 기존 공개 URL·동적 매개변수·Next 예약 파일·채보 에디터와 뷰어 파일명은 유지한다.
- 경로를 바꿀 때 import·테스트·스토리·설정·문서 참조를 함께 맞추고 빌드로 확인한다.
- 홈 전용 화면은 `features/home/components`, 공용 부품은 `components/ui`에 둔다.
- 상세 규칙과 ESLint 검사 범위는 [코드 스타일](./code-style.md)의 명명·import 절을 따른다.

## 기본 작업 흐름

문제·범위 확인 → 코드·문서 수정 → 필수 검사와 실제 동작 확인 → 결과·한계 보고 → 사용자 Git 작업.
이 문서의 변경으로 운영 데이터나 기존 제품 규칙을 변경하지 않는다.
