# NosLog 협업 컨벤션

커밋·브랜치·Issue·PR 작성 기준을 관리한다. 코드 작성과 의존 방향은
[코드 스타일](./code-style.md), 디자인 값과 동작은 [디자인 가이드](./design/README.md),
에이전트 작업 권한과 운영 DB·릴리스 절차는 [AGENTS.md](../AGENTS.md)를 따른다.

## 커밋

```text
<type>: <한국어 설명>

변경 이유와 영향 범위 (필요한 경우)

Closes #123 (관련 이슈를 완료한 경우)
```

| 타입       | 용도                                 |
| ---------- | ------------------------------------ |
| `feat`     | 사용자 기능 추가                     |
| `fix`      | 오류 수정                            |
| `refactor` | 동작을 유지하는 구조 개선            |
| `style`    | 포맷·import 정렬 등 동작 없는 변경   |
| `docs`     | 문서 변경                            |
| `test`     | 테스트 추가·수정                     |
| `chore`    | 개발 도구·설정·의존성·CI 변경        |
| `release`  | 버전 갱신 (`release: NosLog vX.Y.Z`) |

- 제목은 변경 결과를 설명하고 끝에 마침표를 붙이지 않는다.
- 여러 목적을 한 제목에 나열하기보다 검토 가능한 작업 단위로 묶는다.
- 관련 이슈 번호는 선택 사항이다. 완료면 `Closes #123`, 참조면 `Refs #123`을 쓴다.
- 서명·도구 홍보 문구를 커밋·PR·릴리스 본문에 추가하지 않는다.
- 에이전트는 제목과 파일별 `git add` 명령만 제공한다. Git 변경 작업은 사용자가 한다.

## 브랜치와 병합

- 기존 `dev` 개발·`main` 릴리스 흐름을 유지한다.
- 작업 브랜치가 필요하면 `codex/<영문 소문자와 하이픈>`을 기본으로 하되 사용자의 지정 이름을 우선한다.
- 별도 작업 브랜치의 PR은 `dev`, 릴리스 PR은 `dev`에서 `main`으로 보낸다.
- 브랜치 생성·동기화·병합·삭제는 사용자가 한다. 이 문서는 새 병합 방식을 강제하지 않는다.
- GitHub 릴리스는 릴리스 PR이 합쳐진 뒤, `main`의 버전과 태그를 확인하고 게시한다.
  상세한 불변 태그 규칙은 AGENTS.md의 「릴리스」 절을 따른다.

## Issue

기존 기능 제안·버그 제보·데이터 수정 폼을 유지한다. UI·접근성, 리팩터링,
테스트, 개발 환경, 문서 작업에는 해당 전용 폼을 사용한다.

- 문제와 필요한 이유, 작업 범위, 완료 조건을 적는다.
- 검증에 필요한 언어·화면 폭·권한·데이터 상태를 관련된 경우 함께 적는다.
- 비밀값·계정 토큰·DB 주소·개인정보를 첨부하지 않는다.
- 비공개 보안 문제는 공개 Issue에 재현 상세나 비밀값을 올리지 않고 운영자에게 전달한다.
- Issue 작성이 작은 수정의 필수 선행 조건은 아니다.

## Pull Request

[기존 PR 템플릿](../.github/pull_request_template.md)을 사용한다.

- 제목은 커밋과 같은 `type: 한국어 설명` 형식이다. 릴리스 PR은 직전 릴리스 양식을 따른다.
- 문제와 변경 결과를 먼저 설명하고 영향받는 기능·화면을 적는다.
- 버전·DB 마이그레이션·환경 변수·의존성·외부 API 영향 여부를 명시한다.
- 실행한 검사는 결과와 함께 적는다. 실행하지 못한 검사는 이유를 적고 체크하지 않는다.
- 공용 UI 변경에는 Storybook 스토리·동작·접근성 검사와 영향을 받는 화면 검증을 포함한다.
- 토큰과 부품 규칙의 변경은 가이드·결정 기록·테스트를 함께 맞춘다.
- 저장·제출·삭제를 포함하는 E2E는 AGENTS.md의 격리 환경 절차를 따른다.

## 파일·경로 정리

- 코드·스타일 파일과 내부 폴더는 kebab-case, React 컴포넌트 이름은 PascalCase를 쓴다.
- 기존 공개 URL·동적 매개변수·Next 예약 파일·채보 에디터와 뷰어 파일명은 유지한다.
- 경로를 바꿀 때 import·테스트·스토리·설정·문서 참조를 함께 맞추고 빌드로 확인한다.
- 홈 전용 화면은 `features/home/components`, 공용 부품은 `components/ui`에 둔다.
- 상세 규칙과 ESLint 검사 범위는 [코드 스타일](./code-style.md)의 명명·import 절을 따른다.

## 기본 작업 흐름

문제·범위 확인 → 코드·문서 수정 → 필수 검사와 실제 동작 확인 → 결과·한계 보고 → 사용자 Git 작업.
이 문서의 변경으로 운영 데이터나 기존 제품 규칙을 변경하지 않는다.
