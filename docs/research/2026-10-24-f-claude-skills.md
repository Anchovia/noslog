## 10. 스킬 구조의 좋은 관행 8줄

1. 길이: SKILL.md 본문 500줄 이하(공식 24 · Cursor 113), 상시 로드 문서(CLAUDE.md · AGENTS.md)는 200줄 이하(공식 26 · 29 · 34), HumanLayer 는 60줄 미만(130). 길면 규칙이 묻힌다(27).
2. 트리거 설명: description 은 「무엇을 + 언제」, 3인칭, 사용자가 실제로 칠 단어를 앞에(24 · 25 · 100). 1,536자에서 잘리고(25), 약간 적극적으로 써야 덜 놓친다(5). 근접 오답 문장까지 넣어 트리거를 평가한다(5).
3. 체크리스트 + 검증 루프: 복사해서 체크하는 단계 목록, 「검사 → 고침 → 다시 검사」, 단계마다 완료 조건을 명확히(24 · 100). 스크립트로 확인할 수 있는 건 스크립트로(74 sloplint · 82 detect · 42 slop-guard).
4. 예시: 규칙마다 Tell/Why/Fix 또는 전/후 쌍(60 · 81 · 79). 긴 규칙 나열보다 대표 예시 몇 개가 낫다(33).
5. 참조 분리: 상세 패턴 · 단어 목록은 references/ 로, SKILL.md 에서 한 단계 깊이로만 연결, 100줄 넘는 참조는 맨 위 목차(24). 36(70줄 + 참조 3개)이 좋은 견본, 35(약 400줄 한 파일)는 매번 전부 읽혀 비싸다(134).
6. 등급과 예외: P0/P1/P2(37), 면제 불가 / 사유 기록 시 면제(74), 「언제 하지 않나」 · 인용 예시 예외 · 오탐 경고(35 · 37 · 57). 등급이 없으면 사소한 tell 수정이 중요한 수정을 밀어낸다.
7. 금지만 쓰지 말고 대신 할 행동을 쓴다(30 「하지 마」보다 「이렇게」 · 100 금지문은 금지 대상을 떠올리게 함 · 73 「지우기만 하면 빈 페이지도 tell」). 대체품을 특정 글꼴 · 색 이름으로 박으면 그게 다음 tell 이 된다(73) — 우리는 대체값을 「가이드 토큰」으로 가리키면 된다.
8. 평가부터: 스킬 없이 돌려 실패를 기록 → 그 실패만 막는 최소 문구 → 다시 돌림(24 · 31 · 97). 같은 지시를 여러 번 돌려 해석이 갈리면 문구가 약한 것(97). 모델이 원래 하는 행동을 시키는 문장은 지운다(100 · 27).

## 11. 「문서 하나를 매번 읽게」 vs 「스킬 · 훅으로 강제」 — 장단과 근거

**상시 문서(AGENTS.md · CLAUDE.md · `.claude/rules/`)**

- 장점: 늘 맥락에 있어 「읽을지 말지」 판단이 없다. Vercel 측정에서 AGENTS.md 압축 색인 100% 대 스킬 기본 53%(문서 없음과 같음) · 명시 지시 79%, 스킬이 56% 사례에서 아예 호출되지 않음(131). Spence 측정에서도 훅 없는 스킬 활성화 50–55%(132).
- 단점: 매 요청 맥락 비용(29). 길수록 규칙이 묻히고(27 · 34), 지시 수가 늘면 준수율이 떨어진다(139 — 500개에서 최고 모델 약 68%; 130 — 약 150–200개 한계, 저자 주장). 공식 문서가 「강제 설정이 아니라 맥락」이라고 못박음(26). Claude Code 가 CLAUDE.md 를 「관련 없을 수 있음」으로 감싸 넘기기도 한다(130, 저자 관찰).
- 절충: `paths` 로 범위를 건 규칙 파일은 해당 파일을 다룰 때만 로드된다(26). 「AI 티 피하기」를 디자인(`app/**/*.tsx`, `app/styles/**`) · 문구(`lib/i18n/message-catalogs/**`, 공지) · 구현(전체)으로 나누면 상시 비용을 줄인다.

**스킬**

- 장점: 설명만 상시(수십 토큰, 129), 본문은 필요할 때. 긴 패턴 목록 · 전/후 예시 · 감사 절차를 담기 좋다(32 — 디자인 지침을 상시 프롬프트에 두면 비싸서 스킬로 뺐다고 공식이 설명).
- 단점: 자동 호출이 불안정(131 · 132 · 133). 명시 호출(`/이름`)이나 UserPromptSubmit 「강제 평가」 훅을 쓰면 표준 문항 100%까지 올랐으나 소표본(132). 외부 스킬은 공급망 위험(138 — 36.82% 결함, 숨은 지시 · 원격 스크립트).
- 맞는 용도: 「작업 끝에 사람이 부르는 감사」(예: `/ai-tell-review` — 바뀐 화면 · 문구 · 코드만 검사하고 전/후 표로 보고), `context: fork` 로 새 맥락에서 돌리면 쓴 사람의 편향도 줄어든다(27 · 25).

**훅**

- 장점: 결정적, 맥락 비용 0, exit 2 로 막고 사유를 돌려준다(28 · 29). 「요청이 아니라 보장」(29 · 34). 「LLM 을 린터로 쓰지 말라」(130).
- 단점: 정규식 · 스크립트로 판정할 수 있는 것만. 취향 · 문맥 판단(「이 카드는 필요한가」)은 못 한다. 프롬프트 · 에이전트 훅은 판단은 되지만 비용 · 지연이 있고(28), Stop 훅은 연속 8회 막으면 무시된다(28). 리뷰어형 검사는 「늘 뭔가 찾아서」 과잉 수정을 부른다(27).
- 맞는 용도(NosLog 예): Tailwind 기본 스케일 · 임의값 · 인라인 숫자(가이드 1절) grep, 메시지 카탈로그의 금지 표현 · 줄표 · 이중 피동 grep, ko/en/ja 키 누락 검사. 기존 `npm run lint`/테스트에 넣으면 훅 없이도 같은 효과.

**종합(근거에서 나오는 결론, 결정은 아님)**: 짧은 상시 체크리스트(측정상 가장 확실히 적용됨) + 기계적으로 잴 수 있는 것은 린트 · 테스트 · 훅(강제) + 긴 패턴 목록과 감사 절차는 사람이 부르는 스킬(명시 호출). 상시 문서에는 우리 가이드 · 결정에 이미 있는 것을 다시 쓰지 말고 포인터만 둔다(100 — 진실 원천은 한 곳). 외부 스킬은 설치하지 않고 규칙만 우리 말로 옮겨 적는다(138).
