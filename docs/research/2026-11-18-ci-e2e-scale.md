테스트 비율 원칙 글 3곳(가이드 수에 넣지 않음):

- [Google Testing Blog, Just Say No to More End-to-End Tests](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)(2015): 첫 짐작으로 단위 70 · 통합 20 · e2e 10, e2e 는 전체를 확인할 「small number」.
- [Martin Fowler, TestPyramid](https://martinfowler.com/bliki/TestPyramid.html)(2012): UI 를 거치는 e2e 는 깨지기 쉽고 비싸고 느리며 비결정성에 약하니 단위로 훨씬 많이 시험한다.
- [Kent C. Dodds, Write tests. Not too many. Mostly integration.](https://kentcdodds.com/blog/write-tests) · [Testing Trophy](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications): 정적 검사(TypeScript · ESLint)가 많은 확신을 주고, 통합 위주로 쓰되 너무 많이 쓰지 않는다.

## Storybook 을 어디까지 두나 (29곳, 2026-11-18)

판 2(Storybook 지움)를 사용자가 고르지 않고 「내용은 줄여도 되지만 없애면 품질이 떨어진다」 고 해서, Storybook 을 쓰는 서비스가 스토리를 어디에 두고 무엇을 검사하는지 다시 쟀다. 방법은 위와 같은 파일 목록 조회에, 스토리 파일을 최대 40개 골라 `play` 함수가 있는지 보고, `.storybook/` 의 a11y `test` 값과 워크플로의 Storybook · Chromatic 단계를 읽었다. 큰 회사 · 오픈소스 앱 위주다(1인 · 소규모는 위 표에서 Storybook 을 쓰는 곳이 2곳뿐이라).

## 막힌 곳 · 미확인

- `unkeyed/unkey` · `openproject/openproject`: API 가 404 를 돌려줘 세지 않았다.
- Storybook 표의 `play` 는 표본 파일 안 글자 검색이라 실제 상호작용 검사 수와 다를 수 있다. a11y 「애드온」 은 애드온만 있고 `test` 값을 못 찾은 곳이다.
- Zero · onlook 의 e2e 파일, formbricks 의 axe 사용처, osu-web Dusk 테스트 수는 열지 않아 미확인.
- 시간은 성공 실행만 쟀고, 저장소마다 러너(Blacksmith · 큰 러너)가 달라 같은 일의 시간을 견준 값은 아니다.
- NosLog 저장소는 공개라 GitHub Actions 시간 요금이 없다(2026-11-18 `gh repo view` 확인). 줄이는 이득은 기다리는 시간과 실패 소음이다.
